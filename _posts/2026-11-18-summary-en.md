### [Java4Shell: Remote Code Execution Vulnerability in OpenJDK Base64 Processing](https://calif.io/java4shell/) ⭐️ 9.0/10

Calif has disclosed Java4Shell, a remote code execution vulnerability in OpenJDK&\#x27;s Base64 processing, with demonstrated network-based exploitation. The affected condition is specific: HotSpot-based JVMs are vulnerable — including Oracle JDK, OpenJDK builds, and GraalVM — while OpenJ9, GCJ, and Azul Prime \(Zing\), which replaces the C2 compiler, are not. Calif reports the attack was performed over the internet through public IP addresses, not just in laboratory conditions, though exploitation is currently sensitive to network conditions such as round-trip time and jitter, which limits reliability.

hackernews · werrett · Nov 17, 21:11 · [Discussion](https://news.ycombinator.com/item?id=50538240)

**「Background」** Java4Shell \(CVE-2026-114938\) is a memory-corruption flaw in OpenJDK&\#x27;s Base64 decoder that enables unauthenticated remote code execution. The vulnerable code path runs only on x86-64 CPUs supporting AVX-512 VBMI, affecting OpenJDK 17.0.6 and later, Java 21, 25, and 27 before the November 17, 2026 fixes, and Oracle Java SE 8 Enterprise Performance Pack 8u511b33-perf. This matters because Base64 decoding is a ubiquitous operation in Java services, and HotSpot-based builds — Oracle JDK, GraalVM, and other OpenJDK derivatives — are widely deployed in production.

**「Organizations running Java services should check exposure」** Because HotSpot-based JDKs are extremely widely deployed, organizations running Java network services should inventory their JDK builds and apply detection tooling — Semgrep has published free detection scripts targeting the vulnerability&\#x27;s specific conditions. Unconfirmed reports circulating on social media suggest the flaw relates to the AVX512 implementation of Base64 decoding and may be worked around by running Java with -XX:UseAVX=2; treat this workaround as unverified until confirmed by the vendor or researchers.

**「Security community responds with analysis and scripts」** Commenters judged the research impressive but noted exploitation conditions are narrow: one quoted the paper&\#x27;s &\#x27;Remote Heap Feng Shui&\#x27; section showing the attack prefers low, stable round-trip times, while Semgrep&\#x27;s ievans said specific conditions still leave &\#x27;a lot of hosts impacted.&\#x27; Speculation elsewhere in the thread about unconfirmed workarounds and predictions about infrastructure compromise remain unverified opinions rather than established facts.

### [178 major sites served malware via compromised signed Optimizely JavaScript](https://arstechnica.com/security/2026/11/malicious-code-delivered-through-optimizely-hits-visitors-to-hundreds-of-sites/) ⭐️ 8.0/10

Researchers at ReportURI identified 178 websites—including CNN, Zoom, the BBC, and Salesforce—whose visitors were exposed to malware through JavaScript served from cdn.optimizely.com with a valid certificate. The code, injected into Optimizely&\#x27;s digitally signed snippets that run on every customer page, installed multiple payloads that swapped cryptocurrency wallet addresses for attacker-controlled ones, skimmed payment cards, stole cookies and screenshots, and, on iPhones and iPads, delivered iOS exploit kits known as Coruna and DarkSword. How the attackers modified the JavaScript before delivery remains unclear.

rss · Ars Technica · Nov 17, 22:32

**「Background」** Optimizely is a website personalization and experimentation platform whose customers embed Optimizely-provided JavaScript &quot;snippets&quot;—combining company code with customer configuration—into their pages. Because this script runs on every page a customer serves and can be loaded directly from cd.optimizely.com under a valid digital certificate, attackers who modify it gain automatic code execution in visitors&\#x27; browsers across all affected sites, a classic software supply-chain compromise. Researchers at ReportURI documented the resulting multi-purpose kit, which swapped cryptocurrency wallet addresses for the attacker&\#x27;s, skimmed payment cards, stole cookies and screenshots, and delivered the Coruna and DarkSword iOS exploit kits to iPhones and iPads.

**「What this means for site operators」** Because the malicious code carried a valid Optimizely signature and loaded from Optimizely&\#x27;s own CDN, standard code-signing and CDN trust assumptions would not have flagged it, meaning the 178 affected sites cannot rely on those checks to verify snippet integrity. Organizations using Optimizely should review the JavaScript currently being served for injected components before assuming their pages are clean.

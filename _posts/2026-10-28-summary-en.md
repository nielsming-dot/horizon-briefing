### [Critical UEFI firmware flaw in TianoCore EDK II threatens most servers](https://arstechnica.com/security/2026/10/code-execution-flaw-in-uefi-firmware-threatens-most-servers-on-planet-earth/) ⭐️ 9.0/10

A code-execution vulnerability tracked as CVE-2026-97631, rated 9.5 out of 10, has been found in the TianoCore EDK II open source UEFI firmware codebase, which virtually all UEFI suppliers—including AMI, Insyde, and Phoenix—use extensively, along with Microsoft&\#x27;s hardened Project Mu fork. The memory-corruption flaw resides in an ICMP component and can let attackers run malicious code before the operating system and boot-time defenses like Secure Boot and the TPM take effect. Exploited payloads do not persist after running once, but attackers can use the opening to install other payloads that execute early in every boot process. Because EDK II underpins UEFI firmware for most of the world&\#x27;s servers and data centers, the flaw&\#x27;s reach is near-universal.

rss · Ars Technica · Oct 27, 20:25

**「Background: what EDK II is and why boot-time firmware matters」** TianoCore EDK II is the open source reference implementation of the UEFI specification that independent BIOS vendors such as AMI, Insyde, and Phoenix—as well as cloud providers—build their firmware from, meaning a single flaw in its shared code propagates to hardware across the industry. The vulnerable component handles network booting: CVE-2026-97631 is an out-of-bounds write caused by an inaccurate buffer size calculation, triggered when an attacker sends crafted data during a PXE boot process, allowing arbitrary code execution before the operating system loads.

**「Why it matters」** Organizations running servers built on EDK II-derived firmware face a window where malicious code can execute before Secure Boot and TPM-based trust chains are enforced, so defenders should watch for firmware updates from their vendors and apply them as they become available. The lack of payload persistence limits the damage per execution but does not prevent attackers from planting boot-time payloads during an exploit.

An LWN report indicates that CPython&\#x27;s experimental just-in-time \(JIT\) compiler is slated for removal. According to community discussion, the Steering Council had requested a new PEP for the work, and the removal would affect an experimental feature rather than a shipped capability that most Python users rely on today. Commenters noted the JIT had also been viewed as a way to offset the performance penalty from CPython&\#x27;s free-threading initiative.

hackernews · f311a · Oct 27, 11:17 · [Discussion](https://news.ycombinator.com/item?id=50257419)

**「Background」** CPython&\#x27;s experimental just-in-time \(JIT\) compiler was added by Brandt Bucher in early 2024 and has shipped as an experimental feature since the Python 3.13 release. The immediate trigger for its removal is the withdrawal of PEP 836, a Standards Track proposal that would have made the JIT a supported, non-experimental part of CPython once it met measurable performance, compatibility, and maintenance goals. The maintainers withdrew the PEP on October 19 after the steering council rejected the standards-track path, and the JIT code is slated to leave the main branch before Python 3.16 development advances.

**「Impact」** If the removal proceeds, developers counting on the JIT to eventually recover free-threading&\#x27;s single-threaded performance costs would need to rely on existing tools instead; one commenter proposed opt-in, decorator-based Cython-style compilation as a practical alternative for performance-critical functions.

**「Community Discussion」** Commenters argued that CPython&\#x27;s de facto role as the language specification—via its C API and inherited implementation quirks—makes retrofitting a JIT nearly impossible, in contrast to formally specified languages like ECMAScript with multiple implementations. Others, noting Ruby and JavaScript ships JITs, questioned why Python&\#x27;s repeated JIT attempts have struggled, with some suggesting base CPython is already relatively well optimized.

### [Tailscale Discloses SSH Vulnerability Investigation and Fixes](https://tailscale.com/ssh-investigation-update) ⭐️ 7.0/10

Tailscale has published an investigation and remediation update addressing vulnerabilities in Tailscale SSH, the feature that lets the overlay network handle SSH authentication instead of a node&\#x27;s own sshd. The affected path applies specifically to deployments where ACLs grant Tailscale SSH access to a node without granting a path to sudoers or root; users with no SSH access or connectivity to a vulnerable node are not granted access by these issues. Fixes are described as landing in GitHub, so the practical remediation step for operators is updating tailscaled on affected nodes. The precise severity, CVE identifiers, and full scope are not detailed in the available source material.

hackernews · figmert · Oct 27, 19:55 · [Discussion](https://news.ycombinator.com/item?id=50264857)

**「What Tailscale SSH Is」** Tailscale is a mesh VPN built on WireGuard that connects devices through an overlay network, and Tailscale SSH is an optional feature that lets the Tailscale client \(tailscaled\) handle SSH authentication and access control on a node, based on the organization&\#x27;s ACL policies, instead of relying on the standard OpenSSH server \(sshd\) and manually managed keys. Because authentication and network reachability are both governed by the same coordination layer, the vulnerabilities now under investigation apply only to nodes where Tailscale SSH is enabled, not to SSH traffic that simply passes over the overlay network to a regular sshd.

**「What affected users should do」** Organizations running Tailscale SSH should update to Tailscale v1.104.4 or later, where the disclosed vulnerabilities \(TS-2026-014 through TS-2026-017\) are fixed. The flaws can permit credential theft, server crashes, and root privilege escalation, so nodes running older tailscaled versions remain exposed until patched. Several practitioners in the discussion recommend disabling Tailscale SSH in favor of stock OpenSSH with key-only authentication to reduce attack surface, a consideration for teams evaluating how much authentication to delegate to the overlay network.

**「Practitioners Question Delegating SSH to the Overlay Layer」** A former Tailscale employee who now manages the product at an organization reviewed the fixes landing on GitHub and concluded the vulnerabilities only affect setups using ACLs to permit Tailscale SSH into a node without a path to root, with unreachable or unauthorized users gaining nothing. Other commenters, including one who has deliberately stayed on stock OpenSSH with key-only authentication, argued the incident shows the risk of letting Tailscale handle both networking and service authentication; several recommended disabling Tailscale SSH entirely, distributing keys conventionally, or adding a lock-down mode that strips features like SSH, Taildrop, and Taildrive to reduce the attack surface.

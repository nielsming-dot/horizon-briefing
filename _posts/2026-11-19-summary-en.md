### [Unauthenticated RCE vulnerabilities reported in Nginx HTTP/2 handling](https://www.wiz.io/blog/nginx-http2-rce-vulnerabilities) ⭐️ 9.0/10

Researchers reported unauthenticated remote code execution vulnerabilities in Nginx&\#x27;s HTTP/2 handling, tracked as CVE-2026-123633 and CVE-2026-123007. Nginx is one of the most widely deployed web servers, making any unauthenticated RCE in its request handling a critical concern. Community discussion indicates exploitability is constrained — one commenter cited a claim that triggering the bug requires roughly 128 GB of HTTP/2 traffic and specific CPU instructions — and that a simple workaround exists in disabling HTTP/2, which is not enabled by default in Nginx.

hackernews · speedping · Nov 18, 15:19 · [Discussion](https://news.ycombinator.com/item?id=50547374)

**「Background」** HTTP/2 is a binary, multiplexed replacement for HTTP/1.1 that can be enabled in Nginx via configuration; per community data cited in the discussion, it is not enabled by default and roughly 12% of web servers run it. Because the reported vulnerabilities \(CVE-2026-123633 and CVE-2026-123007\) live in the HTTP/2 request-handling code, only Nginx deployments with the protocol turned on are exposed, which is also why disabling HTTP/2 works as a workaround.

**「Impact」** Operators running Nginx with HTTP/2 enabled should treat this as urgent: even if exploitation is difficult, disabling HTTP/2 is a low-cost mitigation, and per w3techs data cited in discussion only about 12% of servers run HTTP/2, so many deployments can turn it off with minimal disruption. Patching to a fixed Nginx version remains the proper fix.

**「Community discussion」** Commenter black3r argued the fix landed in the open source repo about a week before disclosure — with a commit message crediting reporter Xint.io — creating a window where skilled attackers monitoring commits could have reverse-engineered the bug, and criticized the lack of an earlier public service announcement given the simple disable-HTTP/2 workaround. Others downplayed the risk: testtestmetest called it &\#x27;a non issue&\#x27; citing the high traffic requirements, while userbinator blamed HTTP/2&\#x27;s complexity for the bug, arguing its binary, framed protocol is far harder to implement correctly than HTTP/1.x.

**「Background」** Ruby&\#x27;s core string and regular-expression machinery is implemented in C, where buffers are sized ahead of time; case-conversion routines must reserve enough space before writing, since some conversions \(such as upcasing the German sharp s in Windows-1252, which becomes &quot;SS&quot;\) can grow a string.
